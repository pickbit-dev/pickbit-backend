# 모노레포 환경에서 공통 라이브러리를 분리해보기

## 들어가며

이번 백엔드 프로젝트는 Gradle 멀티모듈 기반의 모노레포 구조로 설계했다.  
`user-service`, `product-service`, `auction-service`, `payment-service`, `notification-service`처럼 도메인별 서비스를 나누되, 하나의 저장소에서 함께 관리하는 방식이다.

이렇게 구조를 잡고 나니 자연스럽게 한 가지 고민이 생겼다.

**여러 서비스에서 반복적으로 사용하는 기능을 어디까지 공통화할 것인가?**

서비스가 나뉘어 있어도 요청/응답 DTO, 공통 로깅, 예외 처리처럼 거의 모든 서비스에서 비슷하게 필요한 요소들이 존재한다.  
이런 부분을 매번 각 서비스에 중복해서 작성하는 것은 비효율적이고, 시간이 지날수록 관리 포인트도 늘어난다.

그래서 이번에는 모노레포 구조 안에서 사용할 **공통 라이브러리 모듈**을 직접 구성해보기로 했다.

---

## 왜 공통 라이브러리가 필요하다고 생각했는가

모노레포는 여러 서비스를 하나의 저장소에서 함께 관리하기 때문에, 공통 요소를 통합해서 관리하기에 좋은 구조다.  
특히 프로젝트 초기에는 서비스 간 경계를 나누더라도 설정 규칙, 응답 구조, 예외 처리 방식, 로깅 방식은 비슷하게 가져가는 경우가 많다.

이럴 때 공통 라이브러리가 있으면 다음과 같은 장점이 있다.

- 여러 서비스에서 반복되는 코드를 줄일 수 있다.
- 응답 형식이나 로깅 방식 같은 공통 규칙을 일관되게 유지할 수 있다.
- 새로운 서비스를 추가할 때 기본 골격을 빠르게 맞출 수 있다.
- 공통 로직 수정 시 한 곳에서 관리할 수 있다.

즉, 공통 라이브러리는 단순히 코드를 모아두는 용도라기보다,  
**프로젝트 전체의 개발 규칙을 정리하고 일관성을 유지하는 역할**을 한다고 생각했다.

---

## 하지만 공통화에 너무 의존하면 안 된다고 생각했다

공통 라이브러리를 만들면서 가장 조심하고 싶었던 부분도 분명했다.

**공통화가 지나치면 오히려 각 서비스가 라이브러리에 과하게 종속될 수 있다.**

처음에는 편리해 보여도, 시간이 지나면 서비스마다 요구사항이 달라지고 구현 방식도 달라진다.  
그런데 모든 것을 공통 라이브러리에 밀어 넣기 시작하면, 특정 서비스의 요구사항이 전체 구조를 흔들 수 있고, 결국 라이브러리가 비대해질 가능성이 높다.

그래서 이번 라이브러리는 다음 원칙을 기준으로 설계하기로 했다.

- 여러 서비스에서 반복되지만 비즈니스와 직접적으로 결합되지 않는 기능만 넣는다.
- 서비스마다 달라질 가능성이 큰 구현은 각 서비스에 남긴다.
- 공통 로직은 제공하되, 서비스가 확장하거나 구현할 수 있는 구조를 우선한다.

즉, “많이 넣는 것”보다 **어디까지 공통화할지를 선별하는 것**이 더 중요하다고 봤다.

---

## 이번 라이브러리에서 공통화하기로 한 것

이번에 공통 라이브러리에서 우선 다루기로 한 범위는 다음과 같다.

### 1. 요청/응답 관련 DTO

여러 서비스에서 반복적으로 사용하는 페이징 요청, 페이지 응답, 슬라이스 응답, 정렬 필드 같은 DTO는 라이브러리로 분리하기에 적합했다.

이런 DTO는 특정 도메인에 종속되지 않으면서도 여러 서비스에서 재사용 가능성이 높다.  
특히 목록 조회나 페이징 API는 대부분의 서비스에서 공통적으로 필요하기 때문에, 초기에 정리해두면 구조를 맞추기가 훨씬 수월하다.

### 2. 공통 로깅

HTTP 요청과 응답에 대한 로깅도 공통화 대상에 포함했다.

서비스마다 로그를 남기긴 하지만, 결국 공통적으로 필요한 정보는 비슷하다.

- 어떤 요청이 들어왔는지
- 요청 본문이 무엇인지
- 응답 상태가 무엇인지
- 응답 시간이 얼마나 걸렸는지

이런 부분은 서비스별로 따로 구현하기보다 공통 로거와 설정 클래스로 묶어두는 편이 더 낫다고 판단했다.  
그래서 요청/응답 로거, 로깅 설정 프로퍼티, 로깅 유틸 클래스를 라이브러리 쪽으로 정리했다.

### 3. 공통 예외 처리용 추상 클래스

예외 처리 역시 대부분의 서비스에서 비슷한 흐름을 가진다.

- 검증 실패
- 바인딩 실패
- 타입 불일치
- 잘못된 요청
- 서버 내부 오류

다만 모든 서비스가 완전히 동일한 예외 정책을 사용하지는 않는다.  
그래서 이 부분은 완전히 고정된 구현체로 만들기보다는, **공통 처리 로직을 가진 추상 클래스**로 제공하는 방식을 선택했다.

즉, 라이브러리에서는 기본적인 예외 처리 로직과 `ProblemDetail` 기반 응답 구조를 제공하고,  
실제 서비스에서는 이를 상속받아 서비스 전용 예외를 추가하도록 설계했다.

이 방식의 장점은 명확하다.

- 공통 처리 로직은 재사용할 수 있다.
- 서비스별 확장도 가능하다.
- 응답 형식은 통일하면서도 유연성을 유지할 수 있다.

### 4. Slack 알림용 추상 클래스

추가로 개인적으로 필요했던 기능이 하나 더 있었다.

바로 **Slack 알림**이다.

배포가 완료되었는지, 특정 이벤트가 발생했는지, 혹은 예외적인 상황이 생겼는지를 별도 로그를 열어보지 않고 바로 확인하고 싶었다.  
특히 사이드 프로젝트나 작은 규모의 서비스에서는 이런 알림이 생각보다 유용하다.

그래서 Slack 메시지를 보낼 수 있는 추상 클래스도 라이브러리에 포함했다.  
서비스별로 환경 이름이나 메시지 형식을 다르게 가져갈 수 있도록 추상화하고, 실제 구현은 각 서비스에서 담당하도록 구성했다.

---

## 이번에 잡은 방향

정리하면 이번 라이브러리는 다음과 같은 방향으로 설계하고 있다.

- 공통 요청/응답 DTO를 제공한다.
- 공통 HTTP 로깅 기능을 제공한다.
- 공통 예외 처리용 추상 클래스를 제공한다.
- Slack 알림용 추상 클래스를 제공한다.
- 서비스마다 달라질 수 있는 구체 구현은 각 서비스가 담당한다.

즉, 라이브러리는 **공통 기반을 제공하는 역할**을 하고,  
각 서비스는 그 기반 위에서 자기 책임에 맞게 구현을 확장하는 구조다.

---

## 내가 중요하게 본 기준

이번 공통 라이브러리를 만들면서 가장 중요하게 본 기준은 아래 두 가지였다.

### 공통화는 하되, 과도한 결합은 피한다

공통 코드가 많아질수록 편해 보이지만, 동시에 서비스 간 결합도가 높아질 수 있다.  
그래서 모든 것을 한 번에 공통화하기보다, 반복되지만 독립적으로 유지할 수 있는 것부터 정리하려고 했다.

### 공통화보다 확장성을 우선한다

공통 예외 처리나 Slack 알림처럼 서비스별 차이가 생길 수 있는 기능은 완성된 구현체보다 추상 기반 클래스로 제공하는 편이 더 유연하다.  
이렇게 하면 공통 구조는 유지하면서도, 서비스마다 필요한 기능을 자연스럽게 확장할 수 있다.

---

## 마무리

이번 라이브러리 개발의 목표는 단순히 코드를 한 곳에 모으는 것이 아니다.

모노레포 환경에서 여러 서비스를 함께 운영할 때,  
반복되는 요소를 공통화해서 개발 효율과 일관성을 높이되,  
각 서비스가 공통 모듈에 과하게 종속되지 않도록 경계를 분명히 두는 것이 핵심이다.

즉, 이번 라이브러리는 다음과 같은 역할을 목표로 한다.

- 반복되는 코드를 줄인다.
- 공통 규칙을 정리한다.
- 서비스별 구현은 열어둔다.
- 필요한 부분만 공통화한다.

앞으로는 이 라이브러리에 실제로 어떤 DTO를 넣었는지,  
공통 예외 처리 추상 클래스는 어떤 형태로 구성했는지,  
그리고 요청/응답 로깅을 어떻게 붙였는지 하나씩 정리해보려고 한다.
