실시간 경매 기반 중고거래 플랫폼 백엔드

01 / Overview

단순 CRUD를 넘어선 경매 도메인 중심 백엔드

프로젝트의 핵심 관심사는 “동시에 많은 사용자가 같은 경매에 입찰할 때 데이터 정합성과 사용자 경험을 어떻게 유지할 것인가”였습니다. 인증, 상품, 경매, 결제, 알림을 분리하고 각 도메인의 책임을 명확히 두었습니다.

도메인 분리

인증, 사용자, 상품, 경매, 결제, 알림, 파일 업로드를 독립 실행 가능한 서비스 모듈로 분리했습니다.

실시간 경매

입찰은 REST API로 정합성을 보장하고, 결과는 WebSocket/STOMP로 구독자에게 실시간 전파합니다.

운영 관점 설계

Docker Compose, Caddy, Consul, Redis, Kafka, ELK 기반으로 개발/배포 환경을 분리했습니다.

07 / Engineering Deep Dive

핵심 문제 해결

각 문제를 단순 구현이 아니라 문제 정의, 해결책, 결과 관점으로 정리했습니다.

입찰 동시성 제어

Redisson Lock + JPA @Version

Problem

같은 경매에 여러 사용자가 동시에 입찰하거나, 스케줄러/취소 경로가 같은 Auction row를 수정하면 현재가와 낙찰자 상태가 깨질 수 있었습니다.

Solution

같은 경매 입찰은 Redisson 분산 락으로 직렬화하고, 입찰 외 경로와의 교차 충돌은 Auction 엔티티의 JPA @Version으로 방어했습니다.

Result

입찰 간 정합성을 보장하면서도 스케줄러/취소 등 다른 경로와의 DB row 충돌을 409 Conflict로 감지할 수 있게 했습니다.

입찰 트래픽 안정성

Gateway Rate Limit

Problem

한 사용자가 초당 수십~수백 건의 입찰 요청을 보내면 락 대기열을 점유해 정상 사용자의 입찰 경험을 방해할 수 있었습니다.

Solution

Gateway에서 Redis 기반 RequestRateLimiter를 적용하고, JWT 검증 후 주입한 X-User-Id를 기준으로 사용자별 rate limit을 구성했습니다.

Result

과도한 입찰 요청을 auction-service 앞단에서 차단하고, 서비스 인스턴스 수와 무관한 일관된 제한 정책을 적용했습니다.

WebSocket 실시간 알림 수평 확장

Redis Pub/Sub Bridge

Problem

Spring SimpleBroker는 인스턴스 내부 메모리만 사용하기 때문에 auction-service가 여러 대면 다른 인스턴스에 붙은 구독자는 알림을 받지 못했습니다.

Solution

입찰 성공 이벤트를 Redis Pub/Sub으로 발행하고 모든 auction-service 인스턴스가 구독한 뒤 로컬 WebSocket 브로커로 전달하도록 변경했습니다.

Result

어떤 인스턴스에서 입찰이 처리되더라도 모든 인스턴스의 구독자에게 알림이 도달하며, 100ms debounce로 알림 폭주를 완화했습니다.

OAuth 계정 연결

auth_account / auth_provider_link

Problem

자체 로그인과 카카오 로그인을 함께 지원하면 동일 사용자의 계정이 분리될 수 있고, 이메일만으로 자동 병합하면 보안 리스크가 있었습니다.

Solution

계정 본체와 OAuth provider link를 분리하고, 기존 계정 이메일/비밀번호 인증 후 providerId를 연결하는 명시적 계정 연결 플로우를 구현했습니다.

Result

카카오 account_email 권한이 없어도 사용자가 직접 기존 픽빗 계정에 카카오 계정을 연결할 수 있게 했습니다.

결제 도메인 분리

Auction vs Payment

Problem

경매 종료는 낙찰자 결정이지 거래 완료가 아니며, 결제 취소/미결제를 경매 취소로 처리하면 도메인 의미가 흐려집니다.

Solution

Auction은 낙찰자 결정까지만 책임지고, Payment는 결제 요청/승인/실패/취소 상태를 담당하도록 분리했습니다.

Result

경매 상태와 결제 상태를 독립적으로 표현하고, Toss Payments confirm 및 웹훅 처리 흐름을 명확히 관리할 수 있게 했습니다.

판매자 정산 배치

Spring Batch

Problem

구매확정과 정산완료를 같은 시점으로 처리하면 배치 실패, 이벤트 발행 실패, 재처리 기준을 구분하기 어려웠습니다.

Solution

결제 상태를 ESCROWED → PURCHASE_CONFIRMED → RELEASED로 분리하고, PENDING settlement만 Spring Batch가 처리하도록 구성했습니다.

Result

구매확정 API는 빠르게 종료하고, 정산 완료와 SETTLED outbox 이벤트는 배치 writer에서 원자적으로 처리할 수 있게 했습니다.

Outbox/Inbox 중복 이벤트 처리

Kafka At-least-once

Problem

Kafka consumer 재시작, retry, offset commit 타이밍에 따라 같은 eventId가 여러 번 소비될 수 있어 중복 사용자 생성이나 중복 패널티 적용 위험이 있었습니다.

Solution

도메인 변경과 OutBoxEvent 저장을 같은 트랜잭션으로 묶고, 소비 측은 Inbox.successEventId로 이미 성공 처리한 이벤트인지 먼저 확인하도록 했습니다.

Result

이벤트 전달은 at-least-once를 전제로 두되, consumer handler를 멱등하게 만들어 중복 이벤트가 와도 도메인 상태가 깨지지 않게 했습니다.

09 / Deployment & Operations

개발/배포 환경과 운영 고려

Docker Compose

develop은 로컬 개발 인프라 중심, deploy는 백엔드 서비스와 인프라를 함께 실행하는 단일 서버 배포 구조로 분리했습니다.

Caddy HTTPS

pickbit.co.kr과 api.pickbit.co.kr을 분리하고, Caddy가 HTTPS reverse proxy와 인증서 자동 갱신을 담당합니다.

Secret 관리

DB 비밀번호, OAuth secret, JWT secret, Toss/NCP key는 Git에 포함하지 않고 secret 파일 또는 환경변수로 주입합니다.

Redis 의존성 관리

Redis는 refresh token, OAuth code, 입찰 락, rate limit, WebSocket Pub/Sub, ShedLock에 사용되므로 기능별 key prefix와 장애 영향 범위를 문서화했습니다.

결제 운영 포인트

Toss confirm은 서버 저장 금액과 요청 금액을 비교하고, webhook은 signature 검증 후 DONE/CANCELED/EXPIRED 상태만 안전하게 반영합니다.

정산 배치 운영

Spring Batch는 PENDING settlement만 처리하고, 실패 건은 FAILED로 남겨 원인 확인 후 별도 재처리 대상으로 관리합니다.

인증 전파 기준

Gateway가 JWT를 검증한 뒤 X-User-Id 등 인증 헤더를 downstream으로 전파하고, 각 서비스는 AuthContextHolder로 사용자 컨텍스트를 조회합니다.

11 / Retrospective

배운 점과 개선 방향

What I Learned

  • 실시간 시스템은 정합성, 응답성, 사용자 경험을 함께 고려해야 한다는 점
  • 분산 락만으로는 모든 동시성 문제가 해결되지 않아 DB 레벨 방어가 필요하다는 점
  • OAuth는 provider 권한과 보안 UX를 함께 설계해야 한다는 점
  • 도메인별 책임 분리가 결제/거래 같은 후속 흐름을 명확하게 만든다는 점
  • 이벤트 기반 구조에서는 중복 수신을 정상 상황으로 보고 멱등성을 설계해야 한다는 점

Future Improvements

  • 결제 이후 배송/구매확정/분쟁 처리까지 trade 도메인 고도화
  • 알림 영속성이 필요해질 경우 RabbitMQ STOMP relay 또는 메시지 백로그 구조 검토
  • OAuth provider 확장과 카카오 account_email 권한 확보 후 자동 연결 UX 개선
  • 운영 모니터링 대시보드와 관리자 기능 추가
